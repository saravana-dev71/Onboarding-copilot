## Task 1 — Pin `fastapi-mcp` and `mcp` version in `requirements.txt`

**Rank:** 1 of 5  
**Source:** [`docs/onboarding/verified-setup.md` §8 Failure 1](verified-setup.md) — reproduced on a fresh install  
**Relevant files:** [`booking_system_backend/requirements.txt`](../../booking_system_backend/requirements.txt)

### What is broken

Running `pip install -r requirements.txt` today resolves to `fastapi-mcp==0.4.0` + `mcp==2.2.0`. These two versions are incompatible: `mcp 2.2.0` changed the `Server.__init__()` constructor to accept only one positional argument (`name`), but `fastapi-mcp 0.4.0` still calls it with two (`name`, `description`). This causes every test in [`tests/test_rest.py`](../../booking_system_backend/tests/test_rest.py) (35 tests) to error at collection time, and prevents the Python backend from starting at all.

Exact error, reproduced on this machine:
```
server.py:336: in <module>
    mcp = FastApiMCP(app)
fastapi_mcp/server.py:144: in setup_server
    mcp_server: Server = Server(self.name, self.description)
TypeError: Server.__init__() takes 2 positional arguments but 3 were given
```

Currently passing without this fix: `tests/test_services.py` — 37/37 PASSED.  
Blocked by this bug: `tests/test_rest.py` — 35/35 ERROR.

### What to change

Open [`booking_system_backend/requirements.txt`](../../booking_system_backend/requirements.txt) and add explicit version pins for `fastapi-mcp` and `mcp` so that `pip` always resolves a compatible pair.

**How to find the right pin:**

1. Look up `fastapi-mcp 0.4.0` on PyPI: [https://pypi.org/project/fastapi-mcp/0.4.0/](https://pypi.org/project/fastapi-mcp/0.4.0/)
2. Check its declared `mcp` dependency range. The last `mcp` version before the breaking `2.x` series is the safe upper bound (e.g. `mcp<2.0.0`, or pin to a specific `1.x` release).
3. Alternatively, check whether a newer `fastapi-mcp` (> 0.4.0) already declares support for `mcp 2.x` — if so, upgrading `fastapi-mcp` is also a valid fix.

After editing the file, verify the fix:
```powershell
# From booking_system_backend/
.\.venv\Scripts\python.exe -m pip install -r requirements.txt --upgrade
.\.venv\Scripts\python.exe -m pytest -v --tb=short
# Expected: 72 passed, 0 errors
```

### What to understand first

- **Python version pinning:** `package==x.y.z` locks an exact version; `package>=x,<y` sets a range. Either works here.
- **Where FastApiMCP is used:** [`booking_system_backend/server.py:336`](../../booking_system_backend/server.py:336) — this is the only line that calls `FastApiMCP(app)`. The crash happens at import time (module scope), so it blocks every test that imports `server`.
- **How to run the test suite:** must be run from inside `booking_system_backend/`, not the repo root (see [`AGENTS.md`](../../AGENTS.md) and [`verified-setup.md §5a`](verified-setup.md)).

### Why this task is suitable for a beginner

- **Self-contained:** the entire fix is adding version pins to a single text file.
- **Low-risk:** a version pin cannot break the 37 tests that are currently passing; it can only make the 35 erroring tests pass.
- **Architecturally legible:** `verified-setup.md` documents the exact error, the exact packages, and the exact test command to verify the fix.
- **Level-appropriate:** requires reading PyPI metadata and understanding `pip` resolution — beginner Python skill.

### Potential dependencies / risks

- The contributor must research the correct pin value themselves (or use the suggested starting point above). The specific pin number is not pre-determined here to avoid recommending something untested.
- If `fastapi-mcp` is upgraded to a newer version (rather than `mcp` being pinned down), double-check that its API surface — especially the `FastApiMCP(app)` call at [`server.py:336`](../../booking_system_backend/server.py:336) — is unchanged.

|---|---|---|---|

3. Change `http://localhost:8000` → `http://localhost:8001` in the environment variables table
4. Change `Spring Boot 3.2.0` → `Spring Boot 3.4.1` in the tech stack section

**Also check:** The Docker run example near line 68 contains `-e PYTHON_BACKEND_URL=http://host.docker.internal:8000`. Read [the Docker documentation on `host.docker.internal`](https://docs.docker.com/desktop/networking/#i-want-to-connect-from-a-container-to-a-service-on-the-host) and decide whether this is intentional (Docker network context where the host is accessed via `host.docker.internal`) or a copy-paste error. If the Python backend runs on port 8001 on the host, the correct value would be `http://host.docker.internal:8001`.

### What to understand first

- Open [`booking_system_inventory_hold_service/src/main/resources/application.properties`](../../booking_system_inventory_hold_service/src/main/resources/application.properties) and read line 16:
  ```
  python.backend.url=${PYTHON_BACKEND_URL:http://localhost:8001}
  ```
  The syntax `${ENV_VAR:default}` means: use `ENV_VAR` if set, otherwise use the value after the colon. The default is `:8001`.
- Open [`booking_system_inventory_hold_service/pom.xml`](../../booking_system_inventory_hold_service/pom.xml) and read line 19:
  ```xml
  <version>3.4.1</version>
  ```
  This is inside the `<parent>` block for `spring-boot-starter-parent` — that is the Spring Boot version.

### Why this task is suitable for a beginner

- **Self-contained:** all changes are in one Markdown file (with one optional check in a second file).
- **Low-risk:** documentation fix only; no runtime behaviour changes.
- **Architecturally legible:** the two evidence files (`application.properties` and `pom.xml`) are small and straightforward to read. No knowledge of Spring Boot internals is required.
- **Level-appropriate:** reading a properties file and a POM version declaration are standard beginner Java skills.
