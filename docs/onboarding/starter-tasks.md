## Task 1 — Pin `fastapi-mcp` and `mcp` versions in `requirements.txt` (CRITICAL)

**Rank:** 1 of 5 — highest impact, single-file change, directly unblocks 35 failing tests

### Source

`docs/onboarding/verified-setup.md` — Error 1 (Critical):

> `requirements.txt` does not pin versions for `fastapi-mcp` or `mcp`. Installing today resolves to `fastapi-mcp==0.4.0` + `mcp==2.2.0`. The `mcp 2.2.0` library changed `Server.__init__()` from `Server(name, description)` to `Server(name)`, breaking `fastapi-mcp 0.4.0`.

Verified failure — 35/72 backend tests error with:
```
TypeError: Server.__init__() takes 2 positional arguments but 3 were given
```

### Relevant files

| File | Role |
|---|---|
| [`booking_system_backend/requirements.txt`](../../booking_system_backend/requirements.txt) | Only file that needs changing |
| [`booking_system_backend/server.py:336`](../../booking_system_backend/server.py:336) | Where `FastApiMCP(app)` is called — fails at import |
| [`booking_system_backend/tests/test_rest.py`](../../booking_system_backend/tests/test_rest.py) | 35 tests currently erroring; will pass after fix |

### What the contributor needs to understand

- How Python package version pinning works in `requirements.txt` (e.g. `package==x.y.z`)
- How to identify a compatible `mcp` version: install `fastapi-mcp==0.4.0` in isolation, inspect its declared `mcp` dependency range in its own `setup.cfg`/`pyproject.toml`, then test locally
- How to run the backend test suite: `cd booking_system_backend && .venv/Scripts/python.exe -m pytest -v --tb=short`
- That `fastmcp` and `fastapi-mcp` are separate packages with separate version lines

### Why it is suitable

- **Self-contained:** only `requirements.txt` changes — one file, no logic changes
- **Low-risk:** adding a pin cannot break the 37 passing service tests; it only makes the 35 erroring REST tests pass
- **Architecturally legible:** `verified-setup.md` already describes the exact symptom, root cause, and affected file
- **Level-appropriate:** requires understanding dependency resolution and package APIs — a mid-level contributor should be comfortable reading a package's own metadata to find the right compatible version

### Potential dependencies / risks

- The contributor must determine the correct compatible `mcp` version experimentally (or from `fastapi-mcp`'s changelog) — the report intentionally did not invent a pin
- If `fastapi-mcp` itself has a newer version that already supports `mcp 2.x`, upgrading `fastapi-mcp` instead of downgrading `mcp` is also valid — either is acceptable
- Running the tests requires Python 3.8+ and a working venv (already documented in `verified-setup.md`)
